# .image 产品与技术方案（v0.1）

> 开源项目文档。基于 2026-10-20 的产品讨论整理，实现细节随开发进度更新。
> 本文档描述的是**设计意图**，与代码现状可能有偏差——以代码为准。

---

## 1. 一句话定义

`.image` = 面向理工科的**手写笔记 / 判题 / 纠错三合一**软件：学生在平板上做题、在草稿纸上演算，提交后 AI 判分并**在草稿纸上 in-line 标出"从哪一步开始错"**。

- **平台**：桌面（Windows 优先）+ Android 平板（平板为主）；Chromium 渲染，一套 Web 前端复用。
- **卖点不是"判对错"，而是"判错在哪一步"**。草稿纸是核心资产，不是附属品。

## 2. 核心概念（数据模型底座）

| 实体 | 说明 |
|---|---|
| **Question（题目）** | 从 Word/PDF/OCR 录入，拆成小题；可选**有答案版 / 无答案版**；可带判分步骤（rubric） |
| **QuestionSet（题集）** | 按学科门类粗分类，后期细分章节/来源 |
| **Attempt（作答）** | 一次提交 = 一条记录；**只读存档**，重做 = 新 Attempt |
| **Draft（草稿纸）** | 一题一张，跟题走；三种纸型：白纸 / 稀疏横线 / 代码页 |
| **Stroke（笔迹）** | 原始轨迹（x/y/压感/时间戳/抬笔事件），**提交后立即丢弃** |
| **DraftSnapshot（草稿存档）** | 提交时把草稿渲染成**位图（PNG）**存档，不可修改，用于复习"当时错在哪" |
| **JudgeResult（判题结果）** | 分数（百分制或对错）、首个错点位置、错误标注、三态（对/错/存疑）、提示内容 |
| **WrongBook（错题本）** | 由判错记录聚合而成，离线可看 |

### 2.1 题型与判定规则

| 题型 | 判定方式 | 输出 |
|---|---|---|
| 选择题（按钮作答） | 有答案：**本地比对**，零 token、可离线；无答案：AI 判 | 对/错 |
| 填空题 | 同上（有答案按答案，无答案走 AI） | 对/错 |
| 大题（计算/综合） | 核心输出**对/错（大红叉）**；分数仅作"心理安慰"显示，有评分步骤则参考 rubric | 对错 + 参考分 |
| 证明题 | **出现逻辑错误即停止判断**，输出对/错 + 参考分 | 对错 + 参考分 |

### 2.2 判题的关键规则（用户确认）

- 只定位**第一个出错的步骤**，其后不评（第一步错，后面没意义）。
- 三态：对 / 错 / **存疑**（存疑走二次核验，防冤枉非常规正确解法）。
- 「提示」按钮独立：**按了才给**下一步提示。
- 判完的记录**锁死只读**；重做新开草稿纸。
- 草稿位图 = 复习凭证（"知道我哪一步错了，下次不犯"）。

## 3. 界面结构（1+2+1）

```
┌────┬──────────────┬──────────────┬────┐
│ -1 │      1       │      2       │ +1 │
│用户│  题目+答题区  │  草稿纸/代码页 │工具 │
└────┴──────────────┴──────────────┴────┘
```

| 栏位 | 内容 | 说明 |
|---|---|---|
| **-1 左栏** | 登录、账号、存储位置 | 类似 VS Code 活动栏，可折叠 |
| **1 左主栏** | 题目展示 + 答题区 | 手写写答案与过程；选择题为按钮 |
| **2 右主栏** | 草稿纸（手写）或代码页（机器字） | 三种纸型；判错标注落在这 |
| **+1 右栏** | 公式可视化（LaTeX + 2D/3D 函数图 + 参数旋钮）、terminal（暂缓） | 辅助工具 |

- 平板横屏为主；手机不作为主战场。
- 排版参考 VS Code：可折叠、可拖拽分栏。

## 4. 功能分级

### MVP（先做）
1. 四栏骨架 + 可折叠分栏 + 主题
2. 手写草稿纸（三纸型、压感、撤销/橡皮、缩放滚动、笔迹时序采集）
3. 题目渲染（Markdown + KaTeX）
4. 录入：Word/PDF 导入 + OCR → ipynb 兼容的 cell 结构 → 题库（本地 SQLite）
5. 选择题/填空题判分（本地答案，离线可用）
6. 大题判题链：提交 → 切步骤 → LLM 逐步验证 → 首个错点 + 评分 + 标注
7. 纠错标注 UI：inline 标记 + 小窗 + 提示按钮
8. 判题存档：位图 + 只读记录 + 错题本
9. 设置：API key / 模型 / base_url（BYOK，客户端直连）

### MVP+（第二批）
- 代码页草稿（CodeMirror）与代码题
- 公式可视化：LaTeX + 2D 函数图
- 3D 函数图 + 参数旋钮（WebGL）
- 账号登录（QQ 登录优先；微信需企业资质）
- 服务器同步（题库、作答、错题）

### 后续/暂缓
- Android 壳（Capacitor）
- terminal / ACM 判 AC（用户明确低频，暂不做）
- 微信登录、应用商店上架

## 5. 判题与纠错流程（核心链路）

```
出题 ──► 学生答题（左栏手写/按钮）+ 演算（右栏草稿）
   │
   ├─ 提交（本地先存 Stroke 时序）
   ▼
[有答案?] ──是──► 选择/填空：本地比答案，秒判、离线可用
   │
   否/大题
   ▼
渲染草稿位图（1024~1536 宽）＋题目文本＋rubric（若有）
   ▼
LLM（多模态、流式）：逐步验证 → 首个错点 → 分数/对错 → 标注坐标
   ▼
三态收敛：低置信步骤→二次核验（数值抽查/再问一次）
   ▼
UI 标注草稿（inline 框 + 小窗）＋ 提示按钮
   ▼
存档：位图 + JudgeResult（只读）；丢弃 Stroke；可入错题本
```

要点：
- **步骤切分发生在提交瞬间**（因为轨迹提交即丢弃）。稀疏横线 = 天然行边界；白纸靠笔迹时序+版面聚类；代码页按语法切。
- 标注需要坐标：让模型返回「步骤区域 bbox」或「第几行」，UI 用 SVG 覆盖层画。
- 全流程可流式：先出"对/错"，再逐步出"错在第三步"。

## 6. ipynb 兼容（只借结构，不跑内核）

导入/导出格式对齐 `nbformat`，但 cell 类型自定义（`metadata.image_kind`）：

| cell | 元数据 | 内容 |
|---|---|---|
| 题目 | `question` | Markdown + LaTeX（可含图片） |
| 答案 | `answer` | 手写位图 / 选择项 / 填空文本 |
| 判分步骤 | `rubric` | 分步分值（类似高考评分细则） |
| 作答记录 | `attempt` | 位图 + JudgeResult（`solution` 的概念延伸） |
| 说明 | `note` | 备注 |

好处：用户能拿 Jupyter 打开、能导出给老师；内部渲染不依赖 Jupyter。

## 7. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 渲染 | **Chromium**（桌面 Electron / Android Capacitor 或 Tauri） | 一套 Web 前端双端复用；数学/代码/terminal 生态齐全 |
| UI 框架 | React（或 Vue） | 组件化、生态 |
| 手写 | Canvas 2D + Pointer Events（`getCoalescedEvents`、`pressure`） | 低延迟、可拿笔迹时序 |
| 数学 | KaTeX | 轻、快 |
| 代码页 | CodeMirror 6 | 轻量、可扩展 |
| 3D 函数图 | Three.js / Plotly.js + WebGL | 参数旋钮实时重绘 |
| 本地存储 | SQLite（better-sqlite3 / sql.js） | 离线题库、记录 |
| 同步 | 自建服务器（用户已有） | 账号、题库、记录 |
| 登录 | QQ 互联（个人可申请）；微信需企业资质 | 腾讯系要求 |
| LLM | OpenAI 兼容协议 + BYOK 直连 | 可替换模型、不中转 |

## 8. 架构

```
[客户端 Electron/Capacitor]
   UI 四栏 ─ 手写引擎 ─ 渲染引擎(KaTeX/WebGL/CodeMirror)
      │
      ├─ 本地 SQLite（题库/作答/错题）
      ├─ 判题管线（切步→LLM→三态→标注）
      └─ 直连供应商 API（用户 key，多模态+流式）
                 │
[自建服务器] 账号 / 题库 / 作答同步 ──(不转发 LLM 请求)
```

## 9. 风险与规避

| 风险 | 级别 | 规避 |
|---|---|---|
| 判题冤枉（把对的判错） | 高 | 三态 + 二次核验 + 申诉按钮 + 提示不主动给 |
| 手写识别/理解错误 | 高 | 视觉直判，不做强 OCR；低置信给"存疑" |
| 步骤切分错误 | 中高 | 稀疏横线优先；轨迹时序辅助；白纸降级提示 |
| 同答案两次判分不一致 | 低 | 判分核心是"对/错 + 首个错点"，分数仅作参考，不追求逐分一致 |
| 无答案版大题成本/准确率 | 中 | 明确提示"无答案版为 AI 自评，仅供参考" |
| 手写延迟（平板） | 中 | Canvas 局部重绘、`requestAnimationFrame` 批绘；低端机降采样 |
| 微信登录资质 | 低 | 先 QQ 登录，接口留扩展 |
| Android 跑 Python/C++ | 低 | 不在 MVP 范围（ACM 暂不做） |

## 10. 里程碑

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| M0 | 四栏骨架 + 手写草稿纸 | 平板/桌面上能流畅写、撤销、存档位图 |
| M1 | 题库 + 录入（pdf/docx→ipynb）+ 选择填空判分 | 导入 10 题、离线判分可用 |
| M2 | 大题判题链（视觉 LLM） | 10 道大题中 ≥8 题首个错点定位正确 |
| M3 | 纠错标注 UI + 三态 + 提示按钮 + 位图存档 | 交互闭环，记录只读 |
| M4 | 账号 + 同步（服务器） | 双端同账号、记录可拉取 |
| M5 | Android 壳 | 平板可用 |

# 11. 实现难度评估

> 难度 1（白菜）～5（需要研究）。“工作量大”与“难”分开看。

| 模块 | 难度 | 工作量(人日) | 说明 |
|---|---|---|---|
| 四栏 UI/主题/分栏 | 1 | 3–5 | 纯前端，成熟方案 |
| 手写引擎（压感/撤销/缩放/时序） | 2 | 5–8 | 有大量开源参考（tldraw/excalidraw 思路） |
| 题目渲染 + 三纸型 | 1 | 2–3 | KaTeX + CSS |
| 题库 + 本地存储 | 2 | 3–5 | SQLite，数据模型简单 |
| 录入（docx/pdf/OCR → 小题） | 3 | 5–8 | 切题与公式识别质量是变量 |
| 判题链（切步 + LLM + 三态 + 标注坐标） | **4–5** | 10–15 | **全项目最难**：步骤切分 + 判分一致性 + 标注坐标 |
| 纠错标注 UI | 3 | 4–6 | SVG 覆盖层 + 小窗交互 |
| 选择填空本地判分 | 1 | 1–2 | 纯比对 |
| 错题本 | 1 | 2–3 | CRUD |
| 公式可视化（2D/3D + 旋钮） | 2–3 | 5–8 | WebGL 成熟，3D + 参数联动略费 |
| 代码页 | 2 | 2–3 | CodeMirror 集成 |
| 账号 + 同步（客户端+服务端） | 3 | 6–10 | 用户已有服务器，省去基础设施 |
| Android 壳（Capacitor） | 3 | 5–8 | 平板适配、手写延迟调优 |
| 测试/构建/打包 | 2 | 3–5 |  |

**总评**

- **工程量**：中等偏大。桌面 MVP ≈ 20–30 人日（熟手 + AI 辅助），完整双端 + 同步 ≈ 45–70 人日。
- **技术难度分布**：UI/存储/渲染都不难，**风险全在“判题链”**（步骤切分正确率、判分一致性、标注坐标准确性）。
- **能不能做**：能。没有技术上的死路；最坏情况是判题准确率达不到“学生服气”，需要持续用真实题调 prompt。
- **最大不确定性**：手写数学/物理的视觉理解质量 —— 它决定产品上限，其余都是工程。

# 12. Token / 成本估算

> 两段分开：**A. 开发期消耗**（写这个软件要花多少 token）与 **B. 运行期消耗**（每题判题花多少 token）。均为粗估，假设见每节。

## A. 开发期（用 AI 编码）

假设：TypeScript/React 为主的代码，平均 **6 token/行**；开发过程包含读文件、编译排错、重构、测试，实际消耗约为“净代码 token”的 **3–6 倍**。

| 项目 | 预估代码行数 | 净代码 token |
|---|---|---|
| 桌面 MVP（M0–M3） | ~18,000 | ~110k |
| 完整版（+同步服务器 + Android + 3D 图） | ~32,000 | ~190k |

| 口径 | 估算 |
|---|---|
| 桌面 MVP 全程（含调试/重试） | **0.4M – 1.0M tokens** |
| 完整版全程 | **1.0M – 2.5M tokens** |
| 若按 DeepSeek 价格折算 | 几元 ~ 几十元人民币 |
| 若按 GPT-5 级价格折算 | 几十 ~ 几百元人民币 |

> 注意：上下文缓存（prompt caching）会让重复阅读大幅打折，实际账单通常低于估算上限。

## B. 运行期（用户判题）

假设：一页草稿图 ≈ 1024×1448，high detail 视觉 token ≈ 1,300–1,800。

**单次大题判题 token 明细**

| 组成 | tokens |
|---|---|
| 题目文本 + rubric | 500–1,200 |
| 草稿位图（视觉） | 1,300–1,800 |
| 系统提示 + 输出格式约束 | 300–500 |
| 模型输出（步骤判定+坐标+分数） | 600–1,200 |
| **合计（单次）** | **约 3k – 5.5k** |
| 加二次核验/重试（×1.5–2） | 4.5k – 11k |

**换算成钱（每题）**

| 模型档位 | 单题成本（人民币） |
|---|---|
| 便宜档（DeepSeek / Gemini Flash 级） | **¥0.01 – 0.03** |
| 中档（GPT-5-mini 级） | ¥0.03 – 0.08 |
| 高档（GPT-5 / Claude Sonnet 级） | ¥0.1 – 0.25 |

**场景换算**

| 场景 | 每题 | 每天 50 题 | 每月（30 天） |
|---|---|---|---|
| 便宜档 | ¥0.02 | ¥1 | ≈ ¥30 |
| 中档 | ¥0.05 | ¥2.5 | ≈ ¥75 |
| 高档 | ¥0.15 | ¥7.5 | ≈ ¥225 |

- **选择题/填空题（有答案）**：本地判分，**0 token**。
- **无答案的大题**：模型要先自己解题再判，单题 ≈ 1.3–2 倍，且一致性更差。
- **判题延迟**：单次 3k–5k token，流式输出下用户等待约 3–12 秒（视模型与网络）。

## C. 结论一句话

- 开发期：**百万级 token** 可以把 MVP 做出来，完整版两百万级。
- 运行期：**一题几分钱**，学生一个月几十块 API 费；便宜模型档几乎无感。
